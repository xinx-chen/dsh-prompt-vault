# 从自用到开源：PromptVault 的 WHY / HOW / 知识沉淀

> 结论先行：这不是「做了一个提示词工具」，而是把「我反复解释怎么提问」变成一份可复用资产；真正的产出有三样——一个能用的本地库、一条从需求到 GitHub 的发布路径、一套关于 DSH 插件边界的知识。
> 状态：v1.0 · 2026-11-23 · 证据口径 [实据] / [推断] / [待验证]
> 范围：2026-11-20 需求出现 → 2026-11-23 v0.2.1 结构整理。不含尚未做的多端同步与团队协作。

## 0. 一页看懂

| 问题 | 做法 | 结果 | 代价 |
|---|---|---|---|
| 提示词散在聊天里，用过就找不回 | 侧边栏整页 + 本地 JSON 库 | 可存、搜、标签、常用、复制 | 只在本机，无同步 |
| 同一个提问结构每次重打 | `prompt_vault` 工具 + `prompt-vault` skill | agent 可在对话里提炼、查重、入库 | 一次最多一条，需人工判断 |
| 市面工具不进 DSH 工作流 | 做成 DSH bundle，占侧栏 + 主页面 | 在对话旁边可用 | 依赖 DSH slot/ModuleLoader 契约 |
| 只想自己用，后来想给别人 | MIT + 英文 Host 面 + CI + release | GitHub 公开可安装 | 需长期维护兼容性 |

**一句话边界**：它解决「单机、单用户、在 DSH 里沉淀提示词」，不解决「团队共享、多端同步、提示词市场」。

## 1. WHY：为什么做，而不是记在笔记里

### 1.1 触发：两个需求叠在一起

原话（m00013）：

> 「我想制作一个插件，收藏一些有用的提示词+通过我和你对话中你来根据我的习惯提取一些通用的提示词。」

拆开是两件事：

1. **收藏**：看到好提示词，能存下来、找得到、直接复制。
2. **提炼**：不只存「别人的」，还要从我的对话里抽出「我反复在用的提问结构」。

第二件事才是差异点。普通笔记只能存，不能判断「这段对话里哪一句是可迁移的」。[实据：m00013；实据：`host-skill.js`]

### 1.2 为什么不是笔记 / 表格 / 浏览器书签

| 方案 | 能存 | 能搜 | agent 能读写 | 在对话旁边 | 结论 |
|---|---|---|---|---|---|
| 笔记软件 | 是 | 是 | 否/要插件 | 否 | 存得下，用不起来 |
| 表格 | 是 | 弱 | 否 | 否 | 维护成本高于收益 |
| 浏览器书签 | 是 | 弱 | 否 | 否 | 存的是链接，不是提示词正文 |
| DSH 插件 | 是 | 是 | 是 | 是 | 四个条件同时满足 |

关键不是「存」，是**缩短从「想到一个提问结构」到「下次直接调用」的路径**。路径越短，越可能真的复用。[推断]

### 1.3 为什么是 DSH 插件，而不是独立 App

- 入口在对话侧栏，复制/收藏不用切窗口。
- agent 能通过工具直接写库，不需要我复制粘贴。
- 数据在 `$DSH_HOME`，和会话环境一致，不另起账号体系。
- 代价是绑定 DSH：DSH 的 slot 或 Client 契约一变，UI 可能失效。[实据：README「Compatibility」；推断：维护成本]

### 1.4 为什么后来开源

原话（m00592）：

> 「如何发布为DSH用户都可用的插件，在GitHub上？帮我发布一下」

动机不是「做一个产品」，而是：

1. 代码已经能跑，放着只有自己用，边际成本很低。
2. 「可署名作品」比「本地脚本」更能证明能力。
3. 开源会强迫自己补 LICENSE、README、测试、CI——这些反过来提高质量。

[实据：m00592；推断：署名与质量动机]

### 1.5 非目标（明确不做）

- 不做多端同步：没有账号、没有服务端，数据只在本机。
- 不做团队协作：没有权限、共享、审计。
- 不做提示词市场：不抓取、不推荐、不排名。
- 不做「自动改写你的提问」：只存结构，不替用户做决策。

这些不是「以后一定做」，而是当前版本不承诺；承诺了就要维护。

## 2. HOW：从需求到 release 的五段

### 2.1 五段路径

| 阶段 | 做了什么 | 产出 | 怎么验证 |
|---|---|---|---|
| 1. 需求澄清 | 把「收藏」拆成存/搜/用/提炼；确认点击后只能复制，不能写入输入框 | 功能边界 | 对照 DSH Client 服务目录，确认无 composer 注入 [实据] |
| 2. 技术侦察 | 读 DSH 插件文档、slot 树、Host 服务目录；对比 task-board / meeting-room 的实现 | 技术选型 | 能说清 bundle 与动态插件的差别 [实据] |
| 3. 垂直切片 | 先做 Host：JSON 存储 → HTTP 路由 → agent 工具 → skill；再做 Client 整页 | v0.1.0 可运行 | 存储/路由/工具单测；真实 HTTP；slot 注册 [实据] |
| 4. 开源化 | Host 面英文化、`engines.dsh`、README、LICENSE、CHANGELOG、CI、测试 | v0.2.0 | 13 个测试；`npm pack`；GitHub Actions 成功 [实据] |
| 5. 发布与整理 | 建公开仓库、push、tag/release；按内容重整 `src/`、`assets/`、`docs/` | v0.2.1 | 远程文件核对；模块冒烟；真实库未动 [实据] |

### 2.2 关键决策与代价

| 决策 | 备选 | 为什么选它 | 代价 |
|---|---|---|---|
| 做 bundle 插件 | 动态 Cordis 代码插件 | 需要 Host 持久化 + Client 侧栏页 + agent 工具；bundle 是正式分发形态 | 不能使用动态插件的 `host.call`，Client 要自建 HTTP 通道 |
| 自建 `/prompt-vault` 同源路由 | `@Remote` / task-board 的 connection 鉴权 | meeting-room 已验证的轻量范式，代码少、可控 | 只有同源校验，没有细粒度权限；本地单用户足够 |
| 单 JSON 文件 | SQLite / 浏览器 IndexedDB | 零依赖、可直接备份、Host/Client 都能读 | 无索引、无并发写；靠串行队列和原子写兜底 |
| 侧栏整页 + 剪贴板 | 输入框浮层 / 直接插入 composer | Client 没有 composer 注入服务，硬做会依赖私有 DOM | 多一步粘贴；不能「一键填入」 |
| Host 面英文 | 全中文 | GitHub 面向 DSH 用户，工具描述是 agent 读的，英文更通用 | 中文用户看到的是英文工具输出；UI 仍保留中英双语 |
| MIT | 不开源 / 更严格协议 | 降低使用门槛，方便别人改 | 别人可以闭源使用；不产生直接收入 |
| `src/` + `assets/` + `docs/` | 所有文件堆在根目录 | 代码、静态资源、文档分开；根目录只留入口与包元数据 | 移动文件要同步 `exports`、测试 import、README |

### 2.3 踩过的坑（症状 → 原因 → 处理 → 教训）

| 症状 | 原因 | 处理 | 教训 |
|---|---|---|---|
| 猜的静态路径 `GET /plugins/dsh-prompt-vault/client.js` 返回 404 | 路径不是 DSH 的模块加载路径 | 改用 slot 树确认注册；不把 404 当「插件没加载」 | 验证要看契约，不要猜 URL |
| `curl /` 返回 `dsh web authentication required` | 裸 curl 没有 GUI 会话凭据 | 只把自建路由的 200 当作 Host 证据；页面渲染另验 | 鉴权页的 401/200 不能证明 UI 好坏 |
| Client 里想用 `host.call` 调 Host | `host.call` 属于动态插件的 harness 机制 | 改为同源 `fetch('/prompt-vault/...')` | 先确认「插件形态」再选通信方式 |
| `npm pack` 报 EPERM | 默认 npm cache 里有 root-owned 文件 | 用 `npm_config_cache=/tmp/...` 跑 | 环境问题不要改全局缓存，先隔离 |
| `raw.githubusercontent.com` 20s 超时 | 网络到 raw 域不稳定 | 改用 GitHub API 核对仓库/文件/release | 一个域名失败不等于发布失败 |
| 没有 `gh` CLI | 机器未安装 | 用本机 git credential helper 取凭据，走 GitHub REST | 发布不一定需要 `gh`；但要先确认凭据来源合法 |
| 重载插件后侧栏图标消失 | 重载卸载了旧 Client 模块，页面未刷新 | 刷新 DSH 窗口后重新注册 | Host 重载 ≠ Client 重载；要分开验证 |
| slot 显示 `active:true`，但页面没点过 | 注册成功不等于渲染正确 | 记录为「未验证」，请用户刷新确认 | 不要把「注册」写成「视觉验收」 |

## 3. 知识沉淀：可迁移的部分

### 3.1 DSH bundle 的最小骨架

一个可分发的 DSH 插件，至少要有：

```text
package.json          # name/version/exports/files + dsh.bundle.patch + dsh.client + dsh.engines
cordis.patch.yml      # - insert: [{ id, name }]
index.js              # export function apply(ctx, config)
client.js             # window.__ModuleLoader__.load({ id, factory })
locale/{zh,en}.json   # meta.title / meta.description / meta.detail
icon.svg              # 通过 exports["./icon"] 暴露
```

关键点：

- `exports` 要显式暴露 `"."`、`"./client"`、`"./icon"`、`"./locale/*.json"`、`"./cordis.patch.yml"`；否则 DSH 找不到入口。
- `dsh.bundle.patch` 指向 patch 文件；不要手写 profile 的 `package.json`。
- `dsh.client.inject` 是激活排序，不是服务依赖；真正的依赖在 Client `inject: ['slots','locale']`。
- `dsh.engines.dsh` 写清兼容下限；DSH 还在 alpha，不写就是给用户埋雷。
- 根目录是包元数据，不是代码仓库的杂物间；代码进 `src/`，静态资源进 `assets/`，文档进 `docs/`。

### 3.2 Host 侧：注册即资源，必须可清理

```js
export const inject = ['webServer', 'tools']

export function apply(ctx) {
  const vault = new PromptVault()
  ctx.effect(() => ctx.webServer.register({ kind: 'prefix', path: '/prompt-vault', handler }))
  ctx.effect(() => ctx.tools.register(createPromptVaultTool(vault)))
  // skills / systemPrompt 用 ctx.get() 可选注册
}
```

- 每个注册都包在 `ctx.effect` 里，返回 disposer；插件卸载才能干净。
- `webServer.register` 的 `(kind, path)` 不能重复；prefix 路由自己解析子路径。
- `tools.register` 的定义要含 `parameters`（JSON Schema）、`output.schema`、`output.render`；agent 读的是 render 出来的文本。
- `skills.register` 可能不存在；用 `ctx.get('skills')` 判空，不能因为缺服务就让整个插件加载失败。
- `systemPrompt.section` 的 `order` 要避开内置段；同名同层重复会抛错。

### 3.3 Client 侧：slot 是唯一 UI 扩展点

```js
window.__ModuleLoader__.load({
  id: 'dsh-prompt-vault',
  factory(require) {
    const React = require('react')
    return {
      inject: ['slots', 'locale'],
      apply(ctx) {
        ctx.slots.inject('sidebar.panellist', () => ctx.slots.register({ name: 'sidebar.panellist', id: 'prompt-vault', order: 25 }, Icon))
        ctx.slots.inject('main', () => ctx.slots.register({ name: 'main', key: 'prompt-vault' }, Page))
      },
    }
  },
})
```

- `sidebar.panellist` 是 list，`id` 唯一；`main` 是 keyed，`key` 与侧栏 id 对上就打开整页。
- 两处都用 `slots.inject(...)` 包住 `slots.register(...)`，容忍宿主未声明该 slot。
- Client 没有 composer 注入服务；「点击写入输入框」当前做不到，复制到剪贴板是诚实边界。
- 文案走 `locale.register(ns, {zh,en})` + `locale.bind(ns)`；不要硬编码中文到组件里。
- 主题用 `--dsw-alias-*` token，不要写死颜色；浅色/深色都要能看。
- 不读别的插件 DOM，不 require 客户端 primitives；这是官方 practices 的硬规则。

### 3.4 数据安全：本地文件也要按「会坏」设计

- 写入串行化：所有 mutation 进同一个队列，避免并发写丢数据。
- 原子写：临时文件 + `rename`；不要在目标文件上直接 `writeFile`。
- 损坏恢复：JSON parse 失败时，把原文件改名成 `vault.json.corrupt-<ts>`，再从空库开始；不要静默覆盖。
- 上限：1000 条、正文 20000 字、备注 4000 字、16 个标签；上限写进校验，不靠 UI。
- 去重：按 `content` 判断；同内容 add 返回 `created:false` 和已有 id，避免「收藏两次变两条」。
- 使用次数与更新时间分开：`use` 只加 `uses/lastUsedAt`，不改变 `updatedAt`，否则排序会被「用过」打乱。

### 3.5 开源发布清单（这次实际用到的）

1. 版本号与 CHANGELOG；`private` 去掉。
2. LICENSE（MIT）+ 版权人。
3. `repository` / `homepage` / `bugs` / `keywords`。
4. `engines.node` 与 `dsh.engines.dsh`。
5. README：是什么、装、用、数据、兼容性、开发、边界；英文主文档 + 中文说明。
6. 测试 + CI（Node 22：check → test → pack）。
7. `npm pack --dry-run` 检查发布内容，不让测试数据/临时文件进包。
8. `git init`、commit、remote、push；tag 与 release。
9. 发布后用 API 核对：`private`、默认分支、release、文件列表、CI 状态。
10. 明确写出「未验证」：第二台机器、全新 profile、截图。

### 3.6 测试策略：按「层」测，不按「页面」测

- 存储层：临时目录 + 固定时钟，测 add/去重/update/use/remove/损坏恢复/上限。
- 路由层：真实 `http.createServer`，测 GET/POST、同源/跨源、坏 JSON、超大 body、未知 action。
- 工具层：直接调 `execute`，测六个 action 与返回文本；不启动 DSH。
- Client 层：`node --check` + 假 `window.__ModuleLoader__` 冒烟，确认 factory 能返回、apply 能注册两个 slot；真实渲染仍需浏览器。
- 发布层：CI + `npm pack` + GitHub API 核对。

**没测到的，不要写成「已验证」。** 这次页面视觉就是明确留给用户刷新确认的。

### 3.7 这套经验不能证明什么

- 不能证明「所有 DSH 版本都能装」：只验证了 0.2.3-alpha.2 环境与 CI。
- 不能证明「所有用户都需要它」：目标用户是 DSH 用户，不是通用市场。
- 不能证明「本地 JSON 能撑团队」：单用户假设一破，存储选型就要重做。
- 不能证明「开源就有用户」：发布只是让别人有机会用，不等于有人用。

## 4. 下次做 DSH 插件，直接照这个清单走

- [ ] 先确认扩展点：Host 服务够不够？Client 需要哪个 slot？有没有 composer 注入？
- [ ] 先写最小垂直切片：存储 → 路由 → 工具 → 再 UI；不要先做视觉。
- [ ] 每个注册都包 `ctx.effect`；每个可选服务都 `ctx.get()` 判空。
- [ ] 数据层先做原子写、损坏恢复、上限、去重；这些比 UI 难补。
- [ ] Client 只做「读 state + 发 action」，每次 mutation 用后端返回的完整 state 覆盖。
- [ ] 先跑 `node --check`、单测、真实 HTTP；再做模块冒烟；最后才请人刷新看页面。
- [ ] 发布前补 LICENSE、engines、README、CI、`npm pack --dry-run`。
- [ ] 发布后核对远程文件与 CI，不靠「push 成功」推断「发布成功」。
- [ ] 把「未验证」写进 README 和日志，不用「应该可以」冒充证据。
